# REP-0001: Kernux Founding Engineering Plan

## Status

Accepted for MVP planning.

## Context

Kernux is an AI-native engineering platform aiming to become the operating system for AI products. The founder constraints are one founder, AI-assisted development, Cursor, GitHub, v0.dev, Go, Next.js, PostgreSQL, Redis, and Docker. The MVP should be buildable in approximately one month.

## Executive Recommendation

Build an observability-first modular monolith that ingests AI request traces, stores normalized telemetry in PostgreSQL, exposes an engineering-focused trace explorer and metrics dashboard, and preserves a path toward evaluation workflows and an AI gateway.

## Strategic Scope

| Phase | Product promise |
| --- | --- |
| MVP | See what your AI product is doing. |
| Beta | Measure and alert on AI quality, cost, and latency. |
| v1 | Control AI behavior through routing, evals, and policies. |
| v2 | Operate AI systems across teams, providers, and governance requirements. |

## Recommendation Register

| Recommendation | Why | Benefits | Risks | Alternatives | Trade-offs | Effort |
| --- | --- | --- | --- | --- | --- | --- |
| Observability-first MVP | Tracing is the most immediate cross-provider pain | Fast integration, clear value | Crowded market | Gateway-first, eval-first | Less control initially, more trust | 4 weeks |
| Modular monolith | One founder needs operational simplicity | Faster delivery | Later extraction work | Microservices | Simpler now, less independent scaling | Saves 2-4 weeks |
| PostgreSQL first | Durable, familiar, flexible enough for MVP | Lower stack complexity | Analytics scale limits | ClickHouse first | Faster MVP, future migration possible | Saves 1-2 weeks |
| Redis queues | Enough for simple async work | Quick setup | Weaker durability | Kafka/NATS/SQS | Simpler ops, limited replay | 1-2 days |
| Bring-your-own eval scores | Quality matters but managed evals are complex | Quality dashboards early | Less turnkey | Managed judges now | Faster MVP, less automation | 2-4 days |
| Defer gateway | Traffic-path reliability is high-stakes | Lower risk | Competitors may show routing | Gateway-first | Trust before control | Saves 2-4 weeks |
| Align with OpenTelemetry GenAI | Interoperability is becoming table stakes | Lower lock-in concern | Standards moving | Proprietary schema | More schema care | 2-4 days |

## MVP Definition

The MVP is complete when a developer can:

1. Create a project.
2. Create an API key.
3. Send a trace with spans.
4. View the trace in the UI.
5. Inspect provider, model, prompt, metadata, tokens, cost, latency, errors, and scores.
6. View dashboard summaries.
7. Configure a basic threshold alert.

## Key Risks

| Risk | Mitigation |
| --- | --- |
| Scope creep into gateway/evals | Keep MVP acceptance criteria fixed |
| Trace storage cost | Payload limits, retention, rollups |
| Weak differentiation | Nail first-trace UX and cost/quality connection |
| Poor data model | Design for provider/model/prompt/customer dimensions from day one |
| AI-generated implementation bugs | Tests, review checklists, small PRs |
